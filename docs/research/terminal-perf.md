# ターミナルの欄の速さ、描き方、幅の変更を測った記録

2026-11-12 21:50〜23:45（JST）に測った。対象の issue は #18、#3、#9、#8、#19、#20、#21。数字は、断りが無ければ開発版（`bun tauri dev`、デバッグビルド）の Tauri のウィンドウの中で測った。

## 測り方

| 道具 | 中身 |
| --- | --- |
| `src/term/perf.ts`、`src/term/bench.ts` | 開発版の URL に `?bench=<名前>` を付けると、アプリの中で操作を自動で回し、`FC_PERF_LOG` のファイルに1行ずつ書く |
| `scripts/bench-ccn-pty.ts` | ccn に直接 PTY を作り、claude の入力欄（❯）が出るまでを測る。Claude Town を通さない基準 |
| `scripts/slow-ccn-proxy.ts` | ccn の前に置き、一覧と会話の応答を遅らせる |
| `scripts/mock-ccn-flood.ts` | ccn と同じ口で、決まった出力か記録した出力を流し続ける |
| `scripts/compare-fullscreen.ts` | ccn と同じ形の PTY で claude を2通りに起動し、同じ依頼を出して比べる |

`?bench` の種類は次のとおり。

- `new`: 「＋ 新しい世帯」を押し、❯ が見えるまでの区間を測る
- `open`: 既存のセッションを選び直して開き、描き終えるまでを測る
- `cpu`: ターミナルを30秒開いたまま、IPC の回数と描画の回数を数える。CPU 時間は外から `ps` の差で測る
- `watch`: 40秒、1秒ごとに町の人数と接続の表示を記録する
- `resize`: 右パネルの境目をポインターの操作で動かし、claude が新しい幅で描き直すまでを測る

計測で作ったセッションには `bench-ct-term` の名前を付け、測り終えたら自分の ID だけを止めた。

### 窓が見えないと描画の負荷が測れない

WebKit は、窓が隠れているあいだ描画を止める。本人が全画面の Specter で作業していると、開発版の窓は描かれない。そのため `cpu` は描画の回数（fps）も記録し、描いた回と描いていない回を分けて比べた。描いた回は少ない。

## #18 ターミナルを開くまで

新しい世帯の5回の中央値。cwd はアプリと同じ `~/Documents/meta`。ccn 単体の基準は同じ時間帯に測った。

| 区間（押した時刻からの ms） | 直す前 | 直した後 |
| --- | --- | --- |
| create の応答 | 32 | 40 |
| 一覧に載る（右パネルが出る） | 217 | 48 |
| 最初の size | 242 | 86 |
| 最初の出力 | 800 | 720 |
| ❯ が見える | 1178 | 1153 |
| ccn 単体の ❯ | 1041 | 944 |
| 既存のセッションを開き直して描くまで | 36 | 63 |

普通の状態では、Claude Town の中の待ちは 0.14〜0.21 秒で、もともと大きくなかった。直したのは、一覧に載るのを待たずに create の応答で右パネルを出すことと、前に開いたターミナルの大きさで claude を起動することの2つ。

## #3 メインスレッドの停止

Tauri 2 の説明（Calling Rust from the Frontend）には「Commands without the async keyword are executed on the main thread」とある。ccn の HTTP を待つ命令がメインスレッドで動き、その間は画面が止まっていた。何もしない同期の命令（`perf_ping`）の往復で確かめた。

| 状態 | 直す前 | 直した後 |
| --- | --- | --- |
| 普通（往復の最大、5回の中央値） | 249ms | 15ms |
| 一覧と会話を3秒遅らせた（往復の最大） | 12567ms | 10ms |
| 同じ状態で ❯ が見えるまで | 20 秒たっても開かなかった | 963〜1367ms |

## 一覧の取得の失敗で町が空になる

PR #25 で一覧を3秒で打ち切るようにした後、ノードが一瞬詰まった回に町が「0世帯・0人」になった。失敗しても前回の町を出し続け、続けて失敗したときだけ表示を「つながりにくい」にした。打ち切りは5秒にした。`watch` の40回の記録で比べた。

| 遅らせ方 | 直す前 | 直した後 |
| --- | --- | --- |
| 2回に1回、4秒 | 10回が0人と赤い帯 | 0回 |
| 2回に1回、7秒 | 測っていない | 0回 |
| 15秒後から毎回7秒 | 測っていない | 町は残り、20回が「つながりにくい」 |

## #9 出力を Channel で送る

出力を流し続けるモック（1秒に約90かたまり、約43KB/秒）で、ターミナルを30秒開いた。

| | 直す前 | 直した後 |
| --- | --- | --- |
| 1秒あたりの IPC | 85〜92 | 56〜59 |
| WebContent（描いていない回） | 1.14〜1.24 秒 | 0.75〜1.08 秒 |
| 本体（描いていない回） | 1.31〜1.51 秒 | 1.04〜1.17 秒 |

Channel は 1KB 以上の生のバイト列を fetch でもう1往復して渡し、1KB 未満は数の配列の JSON にする（tauri 2.12.5 の `ipc/channel.rs`）。そのため、Rust で UTF-8 の文字列に戻して JSON で送る形にした。8KB 未満の JSON は1回の eval で届く。

## #8 WebGL で描く

同じモックで、描いた回（30回/秒）だけを比べた。どの欄も1〜2回しか測れていない。

| | 直す前（emit、DOM） | #9 のみ（DOM） | #9＋#8（WebGL） |
| --- | --- | --- | --- |
| WebContent | 3.25〜3.32 秒 | 2.74 秒 | 2.36 秒 |
| GPU のプロセス | 0.94〜0.96 秒 | 0.86 秒 | 0.61 秒 |

直す前から 28% 減った。#8 の終わりの条件の「半分以下」には届いていない。窓が見える状態で回数を増やして測り直す必要がある。

## #19 幅を変えたときの描き直し

ccn の PR #21 を配った後のノードで、`resize` を回した。右パネルの境目を動かし、ターミナルを 76→94→60→76 桁と変えた（3回）。

- どの回も、claude は新しい幅で描き直した。一番長い横線が新しい桁数になり、折り返しの続きになった横線は0行だった
- 大きさを送ってから画面が揃うまでは 19〜51ms だった。送るのは境目が止まってから 150ms 後なので、手を離してから約 0.2 秒で揃う
- 1回のドラッグで送った大きさの通知は1〜2回だった。多すぎも少なすぎもしないので、150ms の待ちはそのままにした
- 開き直したときの replay は、新しい幅（76桁）で描かれていた

窓が隠れていたので、目では見ていない。判定は xterm の画面の中身（横線の長さと折り返し）で行った。

### ほかの画面と幅が違うとき

前は、ほかの画面（ccn.fybe.jp など）が大きさを変えて replay が来るたびに、こちらの大きさを送り返していた。相手も送り返す作りだと、取り合いが続く。次のように変えた。

- ほかの画面が大きさを変えたら、こちらはその大きさに合わせるだけで、送り返さない
- 本人がこちらで打つか、右パネルの大きさが変わったら、こちらの大きさに戻す

後から操作した画面の大きさになる。`resize` で、ほかの画面の変更（50×20）の後に送り返しが0回で、打った後に 76×38 に戻ったことを確かめた。

## #20 fullscreen の描き方との比べ

`scripts/compare-fullscreen.ts` で、claude 2.1.322（`--model haiku`）を 100×30 で起動した。何も付けない起動（default）と、`CLAUDE_CODE_NO_FLICKER=1` を付けた起動（fullscreen）に、同じ依頼（1から40まで1行ずつ）を出した。3回ずつ測った。

| | default | fullscreen |
| --- | --- | --- |
| 返事の間のバイト数 | 18.9〜22.2KB | 6.8〜10.3KB |
| 返事の間のかたまりの数 | 86〜110 | 55〜94 |
| claude の CPU 時間 | 2.80〜4.23 秒 | 2.80〜3.29 秒 |
| 70桁に狭めた後の崩れ（折り返しの横線） | 0行 | 0行 |
| 代替画面（ESC[?1049h） | 使わない | 使う |
| synchronized output（ESC[?2026h） | 70〜90回 | 50〜87回 |

記録した出力をモックから同じ間隔で流し、開発版の CPU を2回ずつ測った（描いていない回）。WebContent は default が 0.50〜0.63 秒/30秒、fullscreen が 0.39〜0.48 秒/30秒だった。本体は 0.37〜0.46 秒と 0.21〜0.29 秒だった。

xterm.js は 6.0.0 で synchronized output（DEC mode 2026）に対応した（リリースノートの PR #5453）。claude はどちらの方式でも ESC[?2026h を出していたので、`CLAUDE_CODE_FORCE_SYNC_OUTPUT` は要らない。

fullscreen は送るバイト数が半分以下で、Claude Town の CPU も少ない。崩れの差は見つからなかった。一方で、fullscreen では会話を claude の中でスクロールし、ターミナルのスクロールバックを使わない。文字の選択とコピーも claude の中の操作になる。どちらを ccn の既定にするかは ccn 側で決める。決める前に、本人が Claude Town の中で fullscreen のスクロールとコピーを試すのがよい。`/tui fullscreen` は設定を保存して以後の全部のセッションを変えるので、試すときは環境変数で起動する。

## #21 予備のセッションを渡すか

採らない。

| | 値 |
| --- | --- |
| 予備1本の待機中の RSS | 820〜850MB（プロセス8個、2回） |
| 予備1本の待機中の CPU | 0.45〜0.52 秒/60秒 |
| 予備で縮む時間 | ccn 単体で ❯ が出るまでの 0.94〜1.04 秒 |

理由は次の3つ。

- 新しい世帯を押すたびに約1秒縮むだけのために、800MB を超えるメモリを使い続ける。軽量化の目標と逆になる
- 押した直後に右パネルとターミナルの欄が出るようになった（#18）。起動中に打った文字はためておき、起動後に流す
- 予備のセッションは cwd が決まった状態で起動するので、町に余分な世帯として出る。隠す作りが要る
